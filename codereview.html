Why do we do Code Reviews?

Code reviews are not just about finding bugs. In fact, automated testing and linters should catch the majority of functional and syntax errors. The primary purposes of a code review are:

Knowledge Sharing — Reviews ensure that more than one person understands how a specific feature works. It breaks down knowledge silos.
Mentorship — It is the single best opportunity for senior engineers to mentor juniors on architecture, idiomatic patterns, and team standards.
Code Maintainability — Reviewers provide a fresh set of eyes to ensure the code is readable and maintainable for the developer who has to touch it 6 months from now.
Shared Ownership — It shifts the responsibility of code quality from the individual author to the entire engineering team.

The "Perfect" Pull Request

If you want your code reviewed quickly and happily by your peers, follow these authoring guidelines:

Keep it Small

A 200-line PR gets a thorough review. A 2,000-line PR gets a "Looks good to me" (LGTM) because the reviewer gave up.

Provide Context

Link the Jira ticket. Include screenshots if UI changed. Explain *why* you chose a specific technical approach.

Review it Yourself

Read your own diff before assigning a reviewer. You will almost always catch a stray comment or typo.

Frequently Asked Questions

How long should a code review take?
As a reviewer, you should try to respond to review requests within 24 hours. The actual act of reviewing should take no more than 30-45 minutes. If it takes longer, the PR is likely too large and should be broken down.
What is "Nitpicking"?
A "Nit" or nitpick is a trivial suggestion, usually regarding naming conventions or slight refactoring. By prefixing a comment with "Nit:", you signal to the author: "This is a minor suggestion, feel free to ignore it if you disagree, and do not let it block the merge."
Who should review my code?
Ideally, you want at least one person who is very familiar with the specific domain/codebase, and potentially one person who is less familiar (to test readability). Two reviewers is generally the sweet spot; more than that leads to diminishing returns and delayed merges.
What if the author refuses to make a change I suggested?
First, jump on a quick call to ensure there's no miscommunication. If it's a matter of subjective style, defer to the team's style guide. If it's functionally correct but you disagree on the approach, consider approving it and discussing the pattern broadly at your next team meeting. Don't block delivery over subjective preferences.
Should we review CSS or configuration files?
Yes. Configuration files (like Terraform, Dockerfiles, or CI/CD YAMLs) are critical infrastructure and absolutely require review. CSS should also be reviewed for proper use of variables, responsive design patterns, and cross-browser concerns.
